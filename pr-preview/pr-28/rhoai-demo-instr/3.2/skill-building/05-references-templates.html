Module 5: Reference Materials and Templates

Learning Objectives

After completing this module, you will be able to:

  • Organize reference files alongside skill definitions

  • Create shared rules that multiple skills can reference

  • Build reusable templates for content generation

  • Use reference paths correctly in skill instructions

  • Leverage user repository templates when available

  • Maintain consistency across related skills

Introduction

Skills become more powerful when they leverage external reference materials and templates. Instead of embedding everything in the main skill file, you can organize supporting materials in a clean, reusable structure.

In this module, you’ll learn how production Showroom skills use references and templates.

Directory Structure for Skills with References

Skills can include supporting files organized in subdirectories:

.agents/skills/showroom-create-demo/
├── skill.md                          # Main skill file
├── workflow.svg                      # Optional workflow diagram
└── references/                       # Supporting reference files
    ├── content-rules.md              # Content quality rules
    ├── conclusion-template.md        # Template for conclusion modules
    └── showroom-scaffold.md          # Showroom setup questions

Benefits of reference files:

  • Keep main skill.md focused and readable

  • Share common patterns across skills

  • Easy to update rules in one place

  • Users can read reference files for details

  • Prevents skill file bloat

Referencing Files in Skill Instructions

Use relative paths with a skill namespace prefix:

Pattern: @namespace/skills/skill-name/references/file.md

Example from create-demo:

**CRITICAL: Content rules** (originality, em dashes, Know/Show bullets vs numbers):

See `@showroom/skills/create-demo/references/content-rules.md` for all rules with correct/incorrect examples.

How Claude resolves these:

  1. Recognizes the @showroom/ namespace

  2. Looks in .agents/skills/showroom-create-demo/

  3. Finds references/content-rules.md

  4. Reads the file to get detailed rules

Benefits:

  • Main skill stays concise

  • Rules are documented with examples

  • Easy to update without changing skill

  • Multiple skills can reference same file

Shared Rules Files

Create common rules that multiple skills reference.

Example: @showroom/docs/SKILL-COMMON-RULES.md

This file contains shared patterns used across create-lab, create-demo, and blog-generate:

# Shared Rules for Showroom Content Skills

## Version Pinning and Attribute Placeholders (REQUIRED)

**NEVER hardcode version numbers or cluster-specific values.**

✅ **CORRECT**:
```asciidoc
OpenShift {ocp_version} includes new features...
Login to {openshift_console_url} with {user}/{password}
```

❌ **WRONG**:
```asciidoc
OpenShift 4.18 includes new features...
Login to https://console.apps.cluster-abc123.com with admin/redhat
```

## Image Path Conventions (REQUIRED)

Images must be stored in `content/modules/ROOT/assets/images/`

**Syntax**:
```asciidoc
image::filename.png[Alt Text,link=self,window=blank,align="center",width=700,title="Caption"]
```

## External Link Format (REQUIRED)

ALL external links use `^` caret to open in new tab:

```asciidoc
link:https://docs.redhat.com/[Red Hat Documentation^]
```

Internal xrefs do NOT use caret:

```asciidoc
xref:03-module-02-next.adoc[Next Module]
```

## Navigation Update Requirements (REQUIRED)

After creating a new module, MUST update `content/modules/ROOT/nav.adoc`:

[Instructions for navigation updates...]

## List Formatting Rules (REQUIRED)

Blank lines required before and after all lists:

[AsciiDoc list formatting examples...]

## Shared Rules

**IMPORTANT**: This skill follows shared contracts defined in `@showroom/docs/SKILL-COMMON-RULES.md`:
- Version pinning or attribute placeholders (REQUIRED)

- Image path conventions (REQUIRED)

User Repository Templates: Priority Override

Skills should prefer templates from the user’s repository over built-in templates.

Pattern from create-lab:

### Step 8: Read Templates and Verification Criteria (BEFORE Generating)

**CRITICAL: Read templates BEFORE generating any content.**

**Template source — check the Showroom repo first:**

The user's Showroom repo may contain a `templates/` directory with up-to-date patterns. Always prefer these over the marketplace's built-in templates.

```bash
# Check if user's Showroom repo has templates
ls {showroom_repo_path}/examples/workshop/templates/ 2>/dev/null
```

**If `examples/workshop/templates/` exists in the Showroom repo — read from there**:
- `{showroom_repo_path}/examples/workshop/templates/index.adoc`
- `{showroom_repo_path}/examples/workshop/templates/03-module-01.adoc`

**If templates do NOT exist — use bundled plugin templates**:
- `@showroom/templates/workshop/00-index-learner.adoc`
- `@showroom/templates/workshop/03-module-01.adoc`

The user's `examples/` directory reflects the latest patterns and may be more current than marketplace copies. Always use the repo's own templates when available.

Why this pattern matters:

  • User’s repo templates are authoritative

  • Org-specific customizations honored

  • Patterns evolve independently

  • Fallback to built-in if missing

Priority order:

  1. User’s repository examples/ or templates/ directory

  2. Skill’s bundled templates in @namespace/templates/

  3. Generic fallback templates

Content Rules in Reference Files

Detailed content rules belong in reference files, not the main skill.

Example: content-rules.md

# Content Rules and Demo Writing Best Practices (create-demo)

**CRITICAL: Content Originality - No Plagiarism**

All generated content MUST be original. Never copy from external sources without proper attribution.

✅ **CORRECT - Original with attribution**:
```asciidoc
According to link:https://kubernetes.io/docs/...[Kubernetes documentation^],
Kubernetes automates deployment. Red Hat OpenShift extends Kubernetes
with enterprise features.
```

❌ **WRONG - Copied without attribution**:
```asciidoc
Kubernetes is an open-source system for automating deployment, scaling,
and management of containerized applications.
```

**CRITICAL: No Em Dashes**

Never use em dashes (—). Use commas, periods, or en dashes (–) instead.

✅ **CORRECT**:
```asciidoc
OpenShift, Red Hat's platform, simplifies deployments.
2020–2025 (en dash for ranges)
```

❌ **WRONG**:
```asciidoc
OpenShift—Red Hat's platform—simplifies deployments.
```

**CRITICAL: Bullets vs Numbers - Know vs Show**

Knowledge sections use bullets (*). Task sections use numbers (.).

[More examples...]

Skills reference specific sections:

**CRITICAL: Content rules** (originality, em dashes, bullets vs numbers, demo language):

See `@showroom/skills/create-demo/references/content-rules.md` for all rules with correct/incorrect examples.

Benefits:

  • Comprehensive examples without bloating skill

  • Easy to update rules independently

  • Users can review rules directly

  • Clear separation of concerns

  • showroom-scaffold.md - Detailed Showroom setup

  • conclusion-template.md - Reusable template structure

Creating Your Own Reference Files

Step-by-step:

  1. Identify repeated patterns across your skills

  2. Extract to shared file in @namespace/docs/

  3. Reference from skills using @namespace/docs/filename.md

  4. Document format - Include examples and anti-patterns

  5. Version control - Keep references updated

Example workflow:

  1. You notice all content skills enforce "no em dashes"

  2. Create @showroom/docs/FORMATTING-RULES.md

  3. Document the rule with correct/incorrect examples

  4. Reference from all skills: "See `@showroom/docs/FORMATTING-RULES.md`"

  5. Update once, applies to all skills

Verification Prompts: Reusable Quality Checks

Reference files can contain verification prompts used across skills.

Example pattern:

File: @showroom/docs/VERIFICATION-PROMPTS.md

## Workshop Quality Verification Prompt

Use this prompt to verify workshop modules:

**File list to read**:
- All `content/modules/ROOT/pages/*.adoc` files
- `content/modules/ROOT/nav.adoc`

**Verify**:
1. All commands students run use `[source,role="execute"]`
2. All images include `link=self,window=blank`
3. No hardcoded credentials or cluster URLs
4. All external links use `^` caret
5. Headings use sentence case
6. Lists have blank lines before/after

**Report**:
- Total modules checked
- Issues found per category
- Files needing correction

Skills reference it:

See `@showroom/docs/VERIFICATION-PROMPTS.md` for verification file lists and usage.
